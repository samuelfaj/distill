
## Visual / interactive objectives

The deliverable looks primarily visual or interactive (a game, a canvas/UI app, a browser page). The harness cannot drive it end-to-end, so do NOT write criteria that require playing or watching it. Anchor the criteria on the static/structural fallback instead: the artifact exists in the source (the page, the game loop, the named controls/bindings the objective lists — keep them verbatim), the pure logic units (physics, collision, input mapping, state transitions) are exercised directly by real unit tests, AND every browser-loaded script provably loads in a browser-like environment — evaluate it headlessly with a `window` global defined and NO Node globals (`module`, `require`), asserting it executes without error and installs its expected globals. A script that only loads under Node (an unguarded `module.exports`) renders a black page and fails the objective. Prefer artifacts that work when the page is opened DIRECTLY from disk (plain `<script src>` over ES modules): `file://` blocks module imports by CORS, so a modules/import-map page is a silent black screen when double-clicked. If ES modules are genuinely needed, the page MUST detect `file:` and display how to serve it instead of failing silently.

For the launch check of a browser page: probe for a headless browser (e.g. `npx playwright --version`); if present, serve and load the page and assert zero page errors, that the render surface's drawing dimensions equal the intended size (catches a renderer that cached a stale/default size), that the surface is SUBSTANTIALLY filled (a high painted fraction or a painted bounding box close to the whole surface — NOT a `> 0 pixels` check), and that a driven input produces the expected visible change; capture a screenshot in `{SCRATCH}`. Module-resolution mistakes (bare specifiers, import maps) surface ONLY on a real page load. Verification steps may add capturable evidence (a screenshot, a DOM dump, a headless-run log) as `evidence`, never as `gating`.
