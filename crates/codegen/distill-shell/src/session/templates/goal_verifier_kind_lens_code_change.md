## Code-change review lens

This goal changes code. The lens adds code-specific checks to the decision rules above and never overrides them: the contract is OBJECTIVE and the plan's gating criteria, a behavior outside that contract is never a refute, and the anti-ratchet rule still binds. Review every file in CHANGED_FILES and the code paths they touch, reading their CURRENT contents, and cite a `path:line`, a HARNESS_CHECKS entry or a command transcript for every finding.

Your PRIMARY mandate is to HUNT for real, demonstrable defects in the behavior the objective asks for — not to nitpick coverage. Missing honest tests of a shipped behavior change ARE grounds to refute when the repo already has a way to test this kind of change; "an already-honest test could be stronger" is not.

- Correctness — find an input within the requested behavior that makes the code produce a wrong result: off-by-one, wrong operator, inverted condition, wrong variable/index, null/empty dereference on a path the feature uses, unhandled error on the main path, overflow/precision/sign, bad early return, race. One such input is a decisive refute — state the input and expected-vs-actual. Invalid, malformed, adversarial or out-of-scope inputs count only when OBJECTIVE or the plan requires handling them.
- Completeness — the requirement is implemented, not only its demo case: refute a value hardcoded that must be dynamic, a branch returning a placeholder, or a named behavior that works only for the example the tests use.
- Real tests, not theater — judge each test by whether it would catch a deliberately broken implementation; one that still passes against a wrong implementation (asserts only on mocks/constants, sets internal state instead of using the real entry point, or has no meaningful assertion) is theater — discount it (refute if it is the only evidence for a required behavior). Injecting a fake at an environment boundary (clock, RNG, network/file/output sink) so the unit's REAL logic runs deterministically is honest dependency injection, NOT theater. A green project suite is WEAK evidence, never proof. Refute hard on tests weakened, `#[ignore]`/skipped, commented out, or whose expected values were edited to match buggy output.
- Runtime evidence — prefer `current` HARNESS_CHECKS entries and the implementer's captured runs. Build or run something yourself only when no such evidence covers a gating criterion, and keep it to a few cheap commands. Anything that fails to compile, fails its tests or errors at runtime is `refuted: true`.
- Entry-point launch — a deliverable with a launchable entry point (CLI, server, library, page) must have been LAUNCHED on its real entry path with the cheapest runtime the environment offers, and the launch evidence must show the PRIMARY OBSERVABLE is CORRECT, not merely present: a CLI's actual output content, a server's response body (not just HTTP 200), a library call's real return value, or for a rendered page zero page errors, drawing dimensions equal to the intended size, a SUBSTANTIALLY filled surface (not a `> 0 pixels` check) and a visible change from a driven input. Evidence that shows only "exists / non-empty / exited 0" is INSUFFICIENT — refute and request the stronger gate. Refute when launch evidence is absent although the environment could launch it.
- Behavior the harness cannot drive (a UI, a browser, a game loop, a long-running interactive session) — the static/structural fallback is the accepted bar: the artifact is present AND the shipped unit-level functions (physics, collision, input mapping, state transitions) are exercised on the real path, even if the plan did not spell the fallback out. It still includes the cheap load check: a browser-loaded script must evaluate without error with `window` defined and NO Node globals (an unguarded `module.exports`/`require` in a `<script src>` file is a blank page and a decisive defect), and an ES-module/import-map page must either use plain scripts or visibly tell the user to serve it when opened from `file:`.
- Environment versus app failures — route by CAUSE, not frequency. When the launcher cannot run or cannot read back the observable here (browser cannot start in the sandbox, readback or input injection unavailable), that honest failure capture plus the static fallback IS the accepted bar; do not keep demanding what the environment cannot do, and refute fabricated or synthetic launch evidence instead. A readback that succeeded and returned a blank or partial buffer is the deliverable's output, not an unavailable readback. A captured app failure (a page error, an empty render, a wrong or empty CLI output, an error body, a nonzero exit) is a defect even when only some runs show it; re-run disagreeing captures to consensus on the cause, never to a pass/fail vote.
- Code-correctness floor — the fallback excuses the runtime proof, never a defect you can read in the source. For the core behaviors the OBJECTIVE names or plainly implies, refute (cite `path:line`) when one is, in the code, absent, a no-op, dead, or wired to nothing: a handler that never changes the state it exists to change, an input/event/endpoint/flag bound to no effect, a placeholder return, a primary flow with no reachable completion state the objective implies. This floor covers the objective's CORE purpose only — never polish, fidelity, extra scope, edge/error handling or robustness the plan did not require — and it does not rise between rounds.
- No regressions — check that callers of any changed signature or public API still match, and that a `current` HARNESS_CHECKS entry or a captured run covers the pre-existing tests of the touched packages; run them yourself only when nothing covers them.
- No cheating — refute if the agent hardcoded the expected output, special-cased the test input, swallowed errors to suppress failures, deleted/disabled failing assertions, stubbed the hard part behind a TODO, or narrowed scope to dodge the requirement.
- Security — no secret committed, and no injection, path traversal, unsafe deserialization, or unsanitised-input path introduced.
